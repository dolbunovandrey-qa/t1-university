# Архитектура учебного проекта

Проект разделён на три Gradle-модуля в ветке `test-architecture`, созданной
от `main` после слияния задания с Allure. За основу взята презентация
`docs/Презентация вебинара. Тема 11. Проектирование и архитектура.pdf`.
Используются обычные Java-классы и наследование: дополнительного DI-фреймворка нет.

## Что находится в каждом модуле

| Модуль | Содержимое |
| --- | --- |
| `common` | `config.json`, `TestConfig`, `ConfigReader`, общий `BaseTest`, коды HTTP и утилита чтения денежных сумм `Money` |
| `api-tests` | `RestApiBuilder`, константы эндпоинтов, `basicapi`-классы, DTO `Good`, `ApiAssert`/`GoodsAssert`, шаги подготовки данных и API-тесты |
| `ui-tests` | PageObject-классы, `PageAssert` и его наследники, шаг авторизации, настройка браузеров, UI-тесты |

Зависимости направлены так: `api-tests → common`, `ui-tests → common + api-tests`.
UI-тестам нужен API-модуль, чтобы создавать и удалять свои товары. API-модуль
не знает о браузере. В `common` нет зависимостей от Selenium или RestAssured.
Общие классы находятся в `src/main/java`, сами тесты — в `src/test/java`.
Ранние упражнения `HomeWorkFirst` сохранены в `common`; они не входят в API/UI-прогоны.

## Как применены рекомендации презентации

На слайде 10 показано разделение на common, api-tests и ui-tests. Именно так
разложены классы и зависимости. На слайдах 14–15 обсуждаются ответственность
классов и общие базовые классы:

- `RestApiBuilder` настраивает адрес, Basic Auth, таймауты, логирование и `AllureRestAssured`.
  Запросы к конкретным эндпоинтам выполняют `GoodsListApi`, `GoodsAddApi`, `GoodsIdApi`.
- `ApiAssert` проверяет статус и сообщения готового ответа. `GoodsAssert`
  добавляет проверки товара и списка. Ассерты не отправляют запросы.
- `BaseTest` предоставляет конфиг и уникальные имена. `ApiBaseTest` отвечает
  за подготовку и уборку API-данных, `UiBaseTest` — ещё и за браузеры.
- `Page` содержит селекторы и действия, а `PageAssert` — проверки. Например,
  проверка текста Alert находится в ассерте, нажатие OK — в `MainPage.acceptAlert()`.
- Парсинг цены вынесен в `Money`, как рекомендует пример с разделением ответственности.

Со слайдами 18 и 20–21 связаны зависимость от `WebDriver`, отдельные бизнес-шаги,
ожидания через Selenide `shouldBe`/`shouldHave`, хранение селекторов в Page и
генерация уникальных названий товаров. Общая авторизация находится в `AuthSteps`,
создание и уборка данных — в `ProductSteps`.

## Конфигурация и тестовые данные

Единственный конфиг магазина находится в `common/src/main/resources/config.json`.
В нём заданы адреса UI/API, пути, логин и пароль, параметры браузера, ожидания,
пагинация, цены, количества, лимит заказа и ожидаемые сообщения.
`ConfigReader.load()` читает его один раз. Цены хранятся как `BigDecimal`,
чтобы не терять точность при расчёте корзины. К имени товара добавляется UUID,
поэтому повторный запуск не вызывает конфликтов уникальности.

Для другого окружения можно использовать полный JSON с той же структурой:

```powershell
.\gradlew.bat runApiSmoke '-Dconfig.file=D:/configs/shop.json'
```

Для разового изменения доступны системные параметры `apiUrl`, `webUrl`,
`headless`, `browser`, `timeout`. Например, показать браузер Selenide:

```powershell
.\gradlew.bat runUiSmoke '-Dheadless=false'
```

Параметр `browser` применяется к обоим наборам: Selenium поддерживает `chrome`,
`edge`, `firefox`, Selenide использует свою настройку браузера. Проверка выполнена
на Chrome. Размер окна и headless-режим берутся из конфига в обоих случаях.
`logging=DEBUG` включает подробное логирование HTTP-запросов.

В коде остаются селекторы и имена полей JSON — это структура приложения.
Коды протокола вынесены в `HttpStatus`. Нули для пустой корзины и число различных
товаров определяются самим сценарием. Границы ранних задач по Java относятся
к их алгоритмам, а не к данным магазина.

## API-покрытие

Список сверён с `/v3/api-docs` приложенного учебного JAR. В тестовом API
пять операций:

| Операция | Класс запросов | Проверки |
| --- | --- | --- |
| `GET /goods/list` | `GoodsListApi` | Формат списка, размер страницы, наличие созданного товара |
| `POST /goods/add` | `GoodsAddApi` | Успешное создание, положительный ID, повторное имя — 400 |
| `GET /goods/{id}` | `GoodsIdApi` | ID, имя, цена; отсутствующий товар — 404 |
| `PATCH /goods/{id}` | `GoodsIdApi` | Изменение имени и цены, повторная проверка GET, ошибки 400 и 404 |
| `DELETE /goods/{id}` | `GoodsIdApi` | Сообщение об удалении, отсутствие товара после удаления, 404 |

Все методы обращения к этим эндпоинтам и все API-проверки имеют `@Step`.
Тесты не используют `given()` напрямую. DTO `Good` задаёт тело POST/PATCH.
Проверка списка больше не требует, чтобы база магазина была пустой.

## UI-покрытие и Allure

По уточнению задания сохранены все существующие UI-сценарии:

- `SelenideTestOne`–`Five`: создание товара, корзина, неверный логин,
  сохранение корзины после обновления, Alert при превышении лимита.
- `SeleniumTestOne`–`Four`: существующие варианты создания товара, корзины,
  неверного логина и обновления страницы на Selenium.
- `Task31`–`Task34`: заказ трёх единиц до 300 рублей, сумма разных товаров,
  создание товара с уведомлением, редактирование с проверкой каталога.
- `DnD`, `ProductRemoval`: перетаскивание в корзину и удаление из неё.

В приложенной презентации есть ссылка на вебинар VI, но нет его отдельных
кейсов. Использован имеющийся в проекте набор без удаления сценариев.

Основные PageObject: `MainPage`, `AdminLoginPage`, `AdminProductsPage`.
Каждому соответствует отдельный класс проверок. Методы действий, бизнес-шаги
и проверки отмечены `@Step`. Allure Selenide Listener записывает действия,
скриншоты и HTML. Для старых Selenium-сценариев вложения при падении делает
`SeleniumFailureAttachments`. `AllureRestAssured` прикладывает HTTP-запросы и ответы,
включая подготовку и уборку UI-данных. AspectJ подключается ко всем тестовым задачам.

## Запуск

Нужны JDK 17 и Chrome для существующих Selenium-тестов. Gradle Wrapper
фиксирует Gradle 8.14. Перед интеграционными тестами нужно запустить JAR стенда.
Для отдельной базы в памяти:

```powershell
java -jar D:/javaless/projects/app/oa_at_train_project-1.0-SNAPSHOT.jar '--spring.datasource.url=jdbc:h2:mem:tests;DB_CLOSE_DELAY=-1'
```

В другом терминале из корня проекта:

| Команда | Что запускается |
| --- | --- |
| `.\gradlew.bat testClasses` | Компиляция всех трёх модулей и тестов |
| `.\gradlew.bat runApiTests` | Все 14 API-тестов |
| `.\gradlew.bat runUiTests` | Все 15 UI-тестов |
| `.\gradlew.bat runAllureTests --continue` | Все API- и UI-тесты |
| `.\gradlew.bat runApiSmoke` | 5 основных API-проверок, по одной на каждую операцию |
| `.\gradlew.bat runUiSmoke` | 5 основных UI-проверок |
| `.\gradlew.bat smoke` | Оба Smoke-набора |
| `.\gradlew.bat runPageObjectTests` | Четыре сценария `Task31`–`Task34` |
| `.\gradlew.bat test` | Все тесты модулей, включая ранние упражнения Java |

Smoke выбирается по `@Tag("smoke")`. UI Smoke проверяет создание товара,
добавление в корзину, неверную авторизацию, лимит и успешный заказ.
Проверка сохранения корзины остаётся в полном наборе. Интеграционные задачи
всегда выполняют запросы к стенду, даже если исходники не менялись.
Каждый тест удаляет созданные им товары; чужие товары не удаляются.

Особенности приложенного JAR важны при повторных запусках: в его
`ProductController` для DELETE с ID 50–53 явно возвращается 500, для GET
с ID больше 100 — также 500, а список из более чем 20 товаров не выдаётся.
Удаление товара не сбрасывает счётчик ID. Поэтому для воспроизводимого
учебного прогона используйте новую базу в памяти и перезапускайте стенд
перед новой серией тестов. Ассерты проверяют настоящие ответы и не принимают
500 за успешную уборку данных.

## Allure-отчёт

Результаты разных задач разделены, чтобы Smoke не смешивался с полным прогоном:
`api-tests/build/allure-results/test`, `ui-tests/build/allure-results/test`
или соответствующие каталоги `smoke`/`pageObjectTests`.

После полного прогона:

```powershell
.\gradlew.bat allureReportZip
```

После Smoke:

```powershell
.\gradlew.bat allureReportZip -PallureResultsTask=smoke
```

Отчёт: `build/reports/allure-report/index.html`. Это один HTML-файл, который
можно открыть после распаковки. Архив: `build/distributions/allure-report-ui-api.zip`.
В него входят отчёт, исходные результаты обоих модулей и это объяснение.
Каталоги `build` и результаты не добавляются в Git.

## Проверка изменений

Проверка выполнена 7 октября 2026 года на JDK 17 и Chrome с приложенным JAR,
в отдельной базе H2 в памяти. Все три модуля компилируются.

| Набор | Всего | Успешно | Падения |
| --- | ---: | ---: | ---: |
| Полный API | 14 | 14 | 0 |
| Полный UI | 15 | 13 | 2 |
| API Smoke | 5 | 5 | 0 |
| UI Smoke | 5 | 5 | 0 |
| Проверки утилиты `Money` | 3 | 3 | 0 |

Дополнительно все 5 API Smoke-тестов прошли с внешним JSON, другим названием
и ценами товаров. Адрес API в JSON был заменён через `-DapiUrl` — проверены
и чтение файла, и приоритет параметра запуска.

`SelenideTestFour` и `SeleniumTestFour` выявляют потерю корзины после обновления:
фактический счётчик становится 0. Это прежнее бизнес-ожидание, поэтому проверки
сохранены и включены в полный прогон. Все четыре `Task31`–`Task34` прошли.
Команда полного прогона завершается с ошибкой из-за этих двух падений;
результаты сохраняются, и Allure-отчёт можно построить следующей командой.

При повторных запусках на одной базе дополнительно воспроизведены 500 для
DELETE с ID 50–53: один UI-тест завершился ошибкой уборки данных, затем три
API Smoke-теста получили тот же ответ. Причина подтверждена проверкой
`ProductController` в JAR. Это ограничение описано выше. Итоговые результаты
в таблице и приложенный Allure-отчёт относятся к прогону на новой базе.

Проверены вложенные `@Step` в результатах обоих модулей и HTTP-вложения,
созданные фильтром RestAssured. В отчёт вошли все 29 API/UI-тестов, включая
два падения, со скриншотами и HTML для диагностики.
