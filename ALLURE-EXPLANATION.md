Внутренняя фабрика HTTP-спецификации не обращается к эндпоинтам. Все методы, непосредственно выполняющие HTTP-вызовы, действия пользователя или ассерты, имеют `@Step`.

## Зависимости и работа аннотаций

В `build.gradle` добавлены:

- `allure-bom:2.33.0` — согласует версии библиотек Allure;
- `allure-junit5` — формирует результаты JUnit 5 в формате Allure;
- `allure-selenide` — записывает события Selenide и диагностику UI;
- `allure-rest-assured` — прикладывает HTTP-запросы и ответы;
- `aspectjweaver:1.9.22.1` — обрабатывает `@Step` и `@Attachment` во время выполнения;
- `allure-commandline:2.33.0` — локальный генератор HTML-отчёта.

Версия Allure 2.33.0 выбрана для совместимости с существующим RestAssured 5.5.6. По [официальной документации Allure RestAssured](https://allurereport.org/docs/restassured/) версии адаптера начиная с 2.34.0 требуют RestAssured 6.x. Обновлять весь HTTP-стек ради отчёта не понадобилось.

Аннотация `@Step` сама по себе не выполняет перехват метода. В задачи Gradle типа `Test` добавляется `-javaagent` с AspectJ, который создаёт шаг при вызове аннотированного метода. Результат проверки записывается в статус этого шага. Как требуется [документацией Allure JUnit](https://allurereport.org/docs/junit-jupiter/), подключён и адаптер тестового фреймворка, и обработчик аннотаций.

`junit-platform.properties` включает автоматическое обнаружение расширений JUnit 5 и отключает параллельный запуск. Все тесты Gradle также запускаются одним процессом без параллельных сценариев: несколько тестов работают с одним стендом, а сценарии пустого списка требуют отсутствия посторонних товаров.

## API: клиент, проверки и вложения

До изменения HTTP-цепочки `given().when().get/post/patch/delete()` и ассерты повторялись в разных тестах и подготовительных методах. Теперь запросы находятся в одном `GoodsClient`.

Каждый публичный метод клиента имеет аннотированный шаг с названием эндпоинта и его значимыми параметрами. Пример:

```java
@Step("POST /goods/add: товар «{name}», цена {price}")
public Response add(String name, BigDecimal price) {
    return request().contentType(ContentType.JSON)
            .body(Map.of("name", name, "price", price)).post("/goods/add");
}
```

В отчёте вместо `{name}` и `{price}` появляются фактические значения. Клиент использует адрес и учётную запись из существующего `config.json`, а `AllureRestAssured` добавляется к каждому запросу явно. Поэтому фильтр работает и в самих API-тестах, и в подготовке данных для UI, и при уборке после теста.

`GoodsAssert` содержит аннотированные проверки HTTP-статуса, сообщения, тела ответа, ID, названия, цены и наличия товара в списке. Сохранены два учебных способа проверки списков: встроенные проверки RestAssured и AssertJ. Отдельный метод проверяет допустимые статусы удаления собственных тестовых данных: 200 или 404, если тест уже удалил товар.

В `api.restassured.task1` и `task2` больше нет прямых HTTP-цепочек и ассертов: тест описывает сценарий и вызывает клиент и класс проверок. В шаг запроса прикладываются HTTP-запрос и ответ с методом, URL, заголовками и телом.

## UI: PageObject, проверки и Listener

Существующая PageObject-архитектура сохранена и расширена. Действия находятся в Page-классах, проверки — в Assert-классах.

Для Selenide аннотированы открытие страниц, ввод логина и пароля, изменение количества товара, кнопки «+»/«−», добавление в корзину, открытие и закрытие корзины, оформление заказа, переход в админку, создание и редактирование товара. Дополнительно добавлены шаги обновления страницы, Drag-and-Drop и удаления товара из корзины.

UI-проверки размечены на обоих уровнях: у проверки бизнес-результата и у общих проверок видимости, значения поля и суммы. Например, проверка строки корзины содержит проверки названия, количества и стоимости. В отчёте виден шаг «Проверить товар в корзине», а внутри — конкретные проверки.

`AllureSelenide` регистрируется в начале каждого теста с настройками:

```java
SelenideLogger.addListener("allure", new AllureSelenide()
        .screenshots(true)
        .savePageSource(true)
        .includeSelenideSteps(true));
```

Аннотированные методы задают понятные названия действий и бизнес-проверок. Listener добавляет вложенные технические события Selenide и при падении прикладывает скриншот и HTML. После завершения теста слушатель удаляется. Настройки соответствуют [документации Allure Selenide](https://allurereport.org/docs/selenide/).

Пакеты `ui.selenide` и `ui.hw7` теперь используют эти же PageObject и Assert-классы. Это распространяет Allure-шаги на ранние учебные сценарии без дублирования селекторов в тестах.

## Сценарии на чистом Selenium

Тесты `ui.selenium` продолжают использовать Selenium WebDriver. Для них добавлены:

- `SeleniumShopPage` — действия и ожидания видимости элементов;
- `SeleniumShopPageAssert` — проверки формы входа, админки, каталога, уведомлений и корзины;
- `SeleniumUiTest` — общие бизнес-шаги открытия магазина и авторизации;
- `SeleniumFailureAttachments` — расширение JUnit 5, прикладывающее скриншот и HTML до закрытия браузера при падении теста.

Действия и проверки Selenium также размечены `@Step`. Скриншот и HTML прикладываются через `@Attachment`, обработку которой обеспечивает тот же AspectJ. В результатах падающего Selenium-теста проверены оба вложения.

Создание драйвера вынесено в `BaseTest`. Режим без окна используется по умолчанию; его можно отключить параметром запуска. Размер окна для обоих вариантов UI — 1280 × 900.

## Общие бизнес-шаги и тестовые данные

`BaseTest` объединяет общие операции для API и UI:

1. Настраивает Selenide и Listener.
2. Создаёт уникальные имена товаров.
3. Создаёт товары через `GoodsClient`, проверяет ответ и регистрирует ID для удаления.
4. Выполняет авторизацию с проверкой видимости формы и введённых значений.
5. Регистрирует имена товаров, создаваемых через UI, до нажатия кнопки создания.
6. Находит такие товары по уникальному имени, при необходимости просматривая несколько страниц API-списка.
7. Удаляет тестовые товары, закрывает оба вида браузеров и снимает Listener.

Очистка выполняется в `@AfterEach`; закрытие браузеров защищено `finally`. Уникальные имена исключают конфликт одинаковых названий между сценариями. Товары, созданные через UI, будут найдены для удаления и при падении последующей проверки уведомления.

`PageObjectTest` сохранён как общий родитель `Task31`–`Task34` с тегом `ui`; повторяющиеся бизнес-методы перенесены из него в `BaseTest`, чтобы ими пользовались остальные тесты.

## Уточнения ранних тестов

При переносе устранены ошибки, мешавшие достоверной проверке:

- В `GoodList` сравнение `name.equals(name)` могло подтверждать наличие любого имени. Теперь AssertJ проверяет наличие конкретного ожидаемого имени.
- Для сценариев 404 прежний выбор `созданный ID + 1` заменён созданием и удалением собственного товара. Это гарантирует отсутствие проверяемого ID, не затрагивая чужие данные.
- В одном Selenide-тесте вызов `is(...)` возвращал boolean, который не проверялся. Теперь счётчик корзины проверяется полноценным ассертом.
- В Drag-and-Drop-сценариях заменены некорректно записанные CSS-селекторы на выбор карточки по ID. Для HTML5-перетаскивания используется поддерживаемый Selenide режим `usingJS()`.
- В Selenium добавлены явные ожидания перед работой с динамически загружаемыми элементами.
- Для цен и расчётов используются `BigDecimal`. Для отображаемых JS-сумм сохранён допуск `0.000000001` ₽, который покрывает погрешность чисел с плавающей точкой и не скрывает ошибку в копейку.

Методы `HomeWorkFirst`, относящиеся к самому первому учебному заданию, также размечены `@Step`. Его тесты не включены в архив UI/API-прогона: задача `runAllureTests` выбирает только теги `ui` и `api`. Стандартная задача `test` остаётся доступна для всего проекта.

Из 15 UI-сценариев прошли 13: создание через админку, наличие товара в каталоге и корзине, неверная авторизация, превышение лимита заказа, Drag-and-Drop, удаление из корзины и четыре задания PageObject.

Не прошли:

| Тест | Ожидание | Фактическое поведение |
| --- | --- | --- |
| `ui.selenide.SelenideTestFour.checkCartItemsAfterReloadTest` | Корзина содержит товар после обновления страницы | Счётчик становится `0`; проверка Selenide завершается ошибкой после ожидания |
| `ui.selenium.SeleniumTestFour.checkCartItemsAfterReload` | Корзина содержит товар после обновления страницы | Счётчик становится `0`; падает AssertJ-проверка |

Причина подтверждена содержимым `index.js` в приложенном JAR: при загрузке страницы выполняется `let cart = []`, а сохранения корзины в постоянное хранилище браузера нет. Оба теста сохраняют прежнее бизнес-ожидание, поэтому этот дефект стенда виден в отчёте. Они не отключены и их ожидание не заменено на пустую корзину.

Из-за двух падений `runAllureTests` возвращает ненулевой код завершения. Это корректное поведение проверки. Отчёт генерируется отдельной командой из уже записанных результатов, поэтому ошибки тестов не мешают передаче отчёта.

## Команды запуска и генерации

Нужны Java 17+, Chrome и Gradle. Локальный Wrapper проекта использует Gradle 8.14. Allure отдельно устанавливать не требуется: задача `installAllure` получает закреплённую версию CLI и распаковывает её внутри `build/tools`.

Для воспроизведения используйте свежий тестовый стенд: проверки пустого списка предполагают пустую БД, а каталог стенда показывает только первые 20 товаров. Запустите стенд в отдельном терминале PowerShell из корня проекта:

```powershell
java -jar ../app/oa_at_train_project-1.0-SNAPSHOT.jar '--spring.datasource.url=jdbc:h2:mem:allure;DB_CLOSE_DELAY=-1'
```

Порт 8080 должен быть свободен. Такой запуск использует временную БД и не меняет обычную файловую базу стенда. Адреса и учётная запись берутся из `src/test/resources/config.json`.

В другом терминале:

```powershell
.\gradlew.bat runAllureTests
.\gradlew.bat allureReportZip
```

Команды выполняются отдельно: генерация отчёта нужна и после прогона, выявившего дефекты. В PowerShell не объединяйте их через условие успешного завершения предыдущей команды.

Дополнительные задачи:

| Команда | Назначение |
| --- | --- |
| `.\gradlew.bat runApiTests` | Только API |
| `.\gradlew.bat runUiTests` | Все UI |
| `.\gradlew.bat runPageObjectTests` | Только `Task31`–`Task34` |
| `.\gradlew.bat test` | Все тесты проекта, включая первое учебное задание |
| `.\gradlew.bat allureReport` | Генерация HTML из последнего `runAllureTests`, без повторного прогона |
| `.\gradlew.bat allureReportZip` | Генерация HTML и ZIP |
| `.\gradlew.bat -Dselenide.headless=false runAllureTests` | UI с видимыми окнами браузера |
| `.\gradlew.bat -PallureResultsTask=runApiTests allureReportZip` | Отчёт из отдельного API-прогона |

При ручном запуске тестов через кнопку IDE учитывайте, что JVM также должен получить AspectJ `-javaagent`; одного импорта `@Step` недостаточно. Для воспроизводимого прогона со всеми настройками используйте указанные задачи Gradle.

## Папки результатов и содержимое архива

Каждая задача `Test` пишет Allure-результаты в `build/allure-results/<имя задачи>`. Перед фактическим новым прогоном очищается только её собственная папка. Поэтому отчёт не смешивает предыдущие UI/API-прогоны и отдельные запуски тестов.

Основные файлы:

- `build/allure-results/runAllureTests` — результаты общего прогона, контейнеры setup/teardown, HTTP-вложения, скриншоты и HTML;
- `build/reports/tests/runAllureTests/index.html` — дополнительный стандартный отчёт Gradle;
- `build/reports/allure-report/index.html` — настоящий HTML-отчёт Allure;
- `build/distributions/allure-report-ui-api.zip` — архив для передачи;
- `ALLURE-EXPLANATION.md` — объяснение изменений.

Генератор используется в режиме `--single-file`: HTML содержит данные и ресурсы внутри себя. Для просмотра распакуйте ZIP и откройте `allure-report/index.html` в браузере; локальный веб-сервер не требуется.

Архив содержит `allure-report/`, `allure-results/` и этот файл. Исходные результаты позволяют повторно сгенерировать отчёт и независимо проверить статусы и шаги. `environment.properties` фиксирует среду запуска.
